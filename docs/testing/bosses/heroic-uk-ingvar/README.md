# 英雄乌特加德城堡：因格瓦尔

更新：2026-09-07；当前状态：隔离 Boss 战已在正常规则下击杀，但含房间前置怪的完整链路尚未验收。UK 绕背、远程绕背、暗影斧规避及坦克持续「猛击后回位」导致坠台的策略修复已实现，仍需在完整链路中回归；测试框架的开局仇恨时序、重启后的实例清理及跨实例传送已有单项验证。当前阻塞点是从斯卡瓦尔德与达隆房间到首领上层骑手平台的可验证地面路线；不会以跨层传送或直线捷径代替正常行走。

## 基线

- 场景 `heroic-uk-ingvar`；map=574，BossEntry=23954，@(245,-333,180.6)。
- 五人普通小队，DungeonDifficulty=heroic(1)，PartySize=5，装备为 early-WLK heroic 档，物品等级上限 200。
- 场景已登记房间门前 3 只骑手（24849；spawn 125934、125935、125940）作为前置清怪目标；Boss 开怪前必须有三者的死亡证据。
- `NavigationWaypoints` 支持把准备点到骑手平台拆为 mmap 地面路径，并要求五名 bot 都到达每一节点才继续；run142 已验证状态机，真实楼梯节点仍待实测后写入配置。
- 机制审计见 [UK 机制审计](../heroic-uk/MECHANICS-AUDIT.md)。

## 完整链路与导航框架

run134、136 已证明前置目标可被框架登记、清理并进入 P2，但 P2 分别因暗影斧伤害与坦克死亡而团灭；这两场不构成完整链路通过。run138 验证了全灭后复活、脱战和装备夹具恢复；run140 验证了死在旧副本的跟随 bot 也会被强制 worldport 到队长的新实例，不再分裂到两个实例。

原准备点与骑手同在上层平台时，普通 bot 移动会发生坠层；把准备点直接降到下层又会失去对上层骑手的视线。因此框架现支持 `NavigationWaypoints = x,y,z[,o]; ...`：每段使用 mmap 的地面寻路，所有成员需在二维 3 码、垂直 4 码内确认到达，才发送下一段或进入夹具和前置战斗。每段有独立的 `NavigationTimeoutSeconds`（默认 60 秒）；死亡、掉队或超时会以 `navigation_failed: waypoint N ...` 写入本次尝试的终态备注。

run142 使用单个准备点作为无位移 smoke test，日志依次出现 `navigation_waypoint_start`、`navigation_waypoint_reached` 和 `before_fixture`，证明状态机不会跳过确认；五名 bot 也通过同一 `Map*` 实例检查。该 run 由人工停止，不能作为战斗结果。

run145 是真实路线勘测：准备点在斯卡瓦尔德与达隆房间 `(109.5,-33.7,118.9)`，目标为骑手平台 `(252.247,-350.532,185.813)`。先用本地 `maps`/`vmaps` 重建了 map 574 的全部 64 个 MMap tile（补出 `5743029.mmtile`），仍得到 `type=17`，即 `PATHFIND_NORMAL | PATHFIND_NOT_USING_PATH`。虽然 fallback 报告的终点坐标与请求相同，它没有多边形地面路径，可能直穿多层几何；框架在发出移动命令前以 `navigation_failed` 中止，未造成任何伤害或拉怪。该失败 attempt 已持久化为 run145/a1，备注保留路径类型和终点坐标。

为定位缺口，run146 对斯卡瓦尔德房间起点做零位移 probe，得到完整路径 `type=1`；run147 对骑手平台做零位移 probe，仍为 `type=17`。这表明 map 574 已加载、起点有效，而上层骑手平台坐标不在可用 MMap 多边形上，不能从已知地面路线抵达。框架新增 `NavigationOnly=true`：最后一个节点到达后记录 `navigation_complete` 并在夹具、前置拉怪和 Boss 战之前结束。run148 在有效房间节点验证了此流程。故正式场景仍不写入任何楼梯节点，不能把 run145–148 记为完整链路通过。

## MMap 资产阻断（2026-09-07）

平台所在的 `5743029.map` 只有 68 字节，已生成的 `5743029.mmtile` 只有 588 字节；重新生成 map 574 的 64 个 MMap tile 并未补出平台碰撞。现有 `clientmpq` 仅有 `common.MPQ`、`common-2.MPQ`、`expansion.MPQ`、`lichking.MPQ`，没有 locale 或 patch MPQ。标准高精度 `vmap4_extractor -l` 因缺少 `Map.dbc` 无法启动；临时单图读取 `574 / UtgardeKeep` 也没有读到 `UtgardeKeep.wdt`，未产生可组装的 UK 矢量几何。

结论是当前本机没有能重提取骑手平台的完整客户端资产。要解除阻断，需要可用的 WotLK 3.3.5 客户端 `Data` 目录，含 locale 的 `Map.dbc`、基础 MPQ 及对应 patch MPQ；随后以该目录重新提取 `maps`/`vmaps`，重建 map 574 MMap，并先用 `NavigationOnly=true` 对平台零位移和整段路线复核。没有这些资产时，不会手工伪造平台碰撞或填写楼梯坐标。

## 神牧是否影响击杀

有影响，但不是本 Boss 当前无法击杀的根因。

run108 是单变量对照：仅将治疗位由 `priest_holy` 替换为 `priest_disc`；同一 ilvl 200 装备、同一其余四人、同一 heroic 难度、Boss 和走位策略。戒律牧使用真言术：盾(263)、快速治疗(255)、苦修(710)三个大雕文，保留原来的三个小雕文；其余角色完全不变。角色快照均通过。

- 神牧 run107：坦克承受首领 30 次直接伤害，共 71,551；106.701s 死亡。神牧在坦克死亡后于 147.147s 死亡。
- 戒律牧 run108：坦克承受 39 次直接伤害，共 112,385；116.218s 死亡，较神牧样本晚 9.517s。戒律牧实际施放苦修(53007) 8 次、真言术：盾(48066) 13 次，自己未死亡。
- 戒律样本的法师在 8.005s 被 31,473 单发击杀、盗贼在 46.417s 死亡；坦克死后只余牧师和萨满，战斗延续到 300s 只能超时。

该单次对照表明：戒律的吸收和苦修确实改善坦克生存窗口，却没有改变“无法击杀”。两次首领随机选人、前方大额伤害的命中序列不同，不能把 9.517 秒差异解释成严格的职业强度结论；要量化职业差异，应在当前 DPS 侧生存问题修复后，对每个治疗各做至少三次独立冷启动样本。

## run116 干净回归

本轮使用 `heroic-uk-ingvar-disc`，与 run108 同为 ilvl 200 五人队和戒律牧；未调整 Boss、装备、难度或施法循环。框架只把正常开怪拆成两个真实 bot 行为阶段：坦克先以 `AttackAction` 开怪，待 Boss 连续锁定坦克满 2,000ms 后，恢复从属 bot 的 `attack tagged` 策略并下达全队攻击。

- 事件表证明时序：坦克首个伤害在 8ms；四个从属 bot 的首个伤害均为 2,017ms；`phase=pull_assist` 为 2,008ms。此前按 tick 计时在本机仅约 43ms 就放行，不能视为有效仇恨窗口。
- 首领施放 P1 猛击(59706) 于 8.004s、20.010s、30.488s、40.723s；P2 暗影猛击(59709) 于 70.017s、88.780s、98.281s、108.353s。战斗覆盖 P1、复活和 P2。
- 盗贼在 98.280s、萨满在 112.714s 死亡；Boss 于 112.716s 被击杀，观察器随后以 Boss 死亡事件及三次连续零血样本确认 `result=kill`。这仍是有伤亡的单场击杀，不能宣称已稳定。

此前 run108 的“无法击杀”并非单由神牧强度决定：其开局 Boss 曾先锁定 DPS，而从属 bot 在坦克第一个有效 GCD 前同 tick 输出。run116 表明，在保持同档装备和机制的前提下，修复真实的坦克优先时序后，戒律牧队伍可完成击杀。下一步应以至少三次独立冷启动回归衡量稳定率，并继续保留“无坦克或无可击杀 DPS”的可审计提前终止条件；不会通过削弱 Boss、提高装备或删除机制获得击杀。

## run130 重启后回归

run130 使用正式场景 `heroic-uk-ingvar`，同一套 heroic5-disc-v1（ilvl 200）配置，在服务器重启后完成 115.014 秒击杀。三名 DPS 阵亡（牧师与坦克存活），但未出现角色或实例夹具异常。

事件记录同时覆盖 P1 的猛击 `59706`（7.891–39.594 秒）与 P2 的暗影猛击 `59709`（72.123–109.322 秒）；这证明经过死亡、安海尔德复活和第二阶段，而不只以 `boss_hp_min=0` 推定击杀。
