## 完整链路与导航框架

run134、136 已证明前置目标可被框架登记、清理并进入 P2，但 P2 分别因暗影斧伤害与坦克死亡而团灭；这两场不构成完整链路通过。run138 验证了全灭后复活、脱战和装备夹具恢复；run140 验证了死在旧副本的跟随 bot 也会被强制 worldport 到队长的新实例，不再分裂到两个实例。

原准备点与骑手同在上层平台时，普通 bot 移动会发生坠层；把准备点直接降到下层又会失去对上层骑手的视线。因此框架现支持 `NavigationWaypoints = x,y,z[,o]; ...`：每段使用 mmap 的地面寻路，所有成员需在二维 3 码、垂直 4 码内确认到达，才发送下一段或进入夹具和前置战斗。每段有独立的 `NavigationTimeoutSeconds`（默认 60 秒）；死亡、掉队或超时会以 `navigation_failed: waypoint N ...` 写入本次尝试的终态备注。

run142 使用单个准备点作为无位移 smoke test，日志依次出现 `navigation_waypoint_start`、`navigation_waypoint_reached` 和 `before_fixture`，证明状态机不会跳过确认；五名 bot 也通过同一 `Map*` 实例检查。该 run 由人工停止，不能作为战斗结果。

run145 是真实路线勘测：准备点在斯卡瓦尔德与达隆房间 `(109.5,-33.7,118.9)`，目标为骑手平台 `(252.247,-350.532,185.813)`。先用本地 `maps`/`vmaps` 重建了 map 574 的全部 64 个 MMap tile（补出 `5743029.mmtile`），仍得到 `type=17`，即 `PATHFIND_NORMAL | PATHFIND_NOT_USING_PATH`。虽然 fallback 报告的终点坐标与请求相同，它没有多边形地面路径，可能直穿多层几何；框架在发出移动命令前以 `navigation_failed` 中止，未造成任何伤害或拉怪。该失败 attempt 已持久化为 run145/a1，备注保留路径类型和终点坐标。

为定位缺口，run146 对斯卡瓦尔德房间起点做零位移 probe，得到完整路径 `type=1`；run147 对骑手平台做零位移 probe，仍为 `type=17`。这表明 map 574 已加载、起点有效，而上层骑手平台坐标不在可用 MMap 多边形上，不能从已知地面路线抵达。框架新增 `NavigationOnly=true`：最后一个节点到达后记录 `navigation_complete` 并在夹具、前置拉怪和 Boss 战之前结束。run148 在有效房间节点验证了此流程。故正式场景仍不写入任何楼梯节点，不能把 run145–148 记为完整链路通过。

## MMap 资产与平台探针（2026-09-07）

候选 vmap/MMap 通过硬链接隔离 DataDir 启动 worldserver，run149 用 `NavigationOnly=true` 在骑手给定坐标做零位移探针。结果仍为 `type=17`、0ms、0 死亡、100% Boss 血量，且没有夹具、前置怪或战斗。因此顶点溢出和错误 tile 名不是唯一根因；给定平台坐标/高度尚未投影到可走多边形。下一步是以该候选 DataDir 对骑手平台做网格和 Z 轴导航探针，记录首个可走点，再据此勘测楼梯分段；在得到实测节点前不填写正式 `NavigationWaypoints`。

### 2026-09-08 源码复核：失败类型与诊断方案

本轮仅分析，未编译、启动服务器或新增战斗样本；进程与 FIFO 核验未发现运行中的 worldserver。复核版本：管理库 `0a7b57b`、core `413bea61`、playerbots `22c1beab`、raidtest `ef037da`，分析开始时四库工作区均干净。

需要收窄此前结论：run145–152 的失败证明当时查询未取得严格路线，不能仅由 `type=17` 推定整个平台没有多边形，亦不能仅由部分路径推定两端拓扑断开。后续局部扫描已经发现两端附近可投影，但缺少能区分以下原因的持久化证据。

- `PathGenerator.cpp:177`：navmesh/query 不可用、忽略寻路状态或起终点 tile 未加载均会返回 `NORMAL | NOT_USING_PATH`。`:275` 的端点投影失败也可能返回同一类型；Player 在该分支使用非 Creature 的 fallback。必须记录具体失败分支、tile 实际加载状态、起终点 polyRef 和投影距离。
- `PathGenerator.cpp:238`：初始投影搜索的垂直半径为 5，失败后扩大到 50；多层场景应记录命中的楼层与投影高度，不能只检查 polyRef 非零。世界坐标到 Detour 的转换为 `{y,z,x}`。
- `MMapMgr.cpp:130` 查询节点池为 1,024；`PathGenerator.h:39` 在 `MOD_PLAYERBOTS` 下多边形和路径点数组上限均为 148。`BuildPolyPath` 主要判断失败位与最终 polyRef，没有持久化 `DT_OUT_OF_NODES`、`DT_BUFFER_TOO_SMALL`、`DT_PARTIAL_RESULT`。这些是待排除因素，尚未证明本案触发。
- `AttemptRunner.cpp:979` 起的循环逐人验证后立即调用 `MovePoint`，与“全员通过后再移动”的注释不符：后续成员验证失败时，前面的成员已收到移动命令。这是独立的框架风险，不能解释平台网格缺口；建议改为全员预检通过后统一发令，失败时统一停止。

建议下一步按顺序执行：

1. 固定候选 DataDir、提取器/生成器版本、配置与资产哈希，核验相关 tile 的文件头及实际加载结果。用相同地面过滤器、明确楼层的两端投影作为诊断输入，先排除加载与投影问题。
2. 在加载完整相关 tile 的网格上，沿真实 Detour 邻接链接做两端有向可达性遍历；同时记录原始 findPath 状态、输出长度和末端 polyRef。将查询资源不足、过滤器排除、缺失 tile 和真正的连通缺口分开。不得将欧氏距离近的多边形直接连边。
3. 若可达但现有查询截断，优先沿已验证走廊分段，或按实测资源需求修正查询限制；若确有缺口，导出断口附近碰撞三角形与 Recast 网格，定位是输入缺面、栅格化/侵蚀/台阶过滤还是 tile 接缝丢失，再做 map 574 范围的最小修复。1600 分辨率消除了顶点溢出，但不能据此认定楼梯细节和连通性已经正确。
4. 仅在证实存在正常游戏中的跳跃、落差或动态过渡时考虑 off-mesh connection/对应正常移动行为；不得用连接横跨缺失楼梯。普通步行段修复后再生成 NavigationWaypoints，并先验收五人 NavigationOnly，再做三骑手和双阶段 Boss 的冷启动完整链路。

当前唯一阻塞是下层房间至骑手平台的正常地面过渡，不能以猜测坐标、跨层传送或直线捷径绕过。先对两端做服务端双向连通分量与场景过渡机制分析；仅在根因可复现后提交最小修复，并以冷启动、三名骑手前置怪、P1→复活→P2 的完整链路回归验收。临时扫描和过程记录不再单独提交。

#### 1. 失败的实际幅度：三场团灭停在 Boss 7–13%

除 6578（74.2 秒失去一名 DPS，停在 39%）外，其余三场团灭分别停在 10%、13%、7%。两阶段各需 247,626 点，团灭场的总输出已达 455k–470k。**当前不是"打不过"，而是差最后 20–35 秒的存活。**

#### 2. P1/P2 输出差距的机制来源：`59709` 是全队控制

P1 六场完全一致：247,626 点、36.7–42.8 秒，raid DPS 约 5,800–6,700。P2 同样 247,626 点，raid DPS 只有 2,551–5,389。

`ingvar_smash_cast` 与 `ingvar_dark_smash_cast` 的 250ms 采样给出直接对照：

- P2 的 `59709` 从**读条起始那一刻**起把全部五人置为 `can_move=false`，包括 reach 校正后距 Boss 28.83 码的治疗（run249 108.360s 全员 true → 108.606s 全员 false）。run249 的 playerbots 拒绝日志此前已记录 `control_auras=stun:59709`。

#### 3. 暗影斧时序：第一把必定落在控制窗口内，第二把才是杀手

六场的第一把斧全部落在 P2 首次 `59709` 之后**恰好 +1.99~2.00 秒**：68.22→70.21、65.18→67.17、65.02→67.01、68.98→70.98、68.21→70.21、70.99→72.99。也就是说，第一把斧出现时全队必定处于 `59709` 控制中，正常角色无权启动规避。

但这不是致命项：**六场中第一把斧没有杀死任何人**。真正致命的是第二把（脚本 `events.Repeat(35s)`），落点在 102.0–108.6 秒；出现第二把斧的四场里，它每场都至少杀死一人，且与是否撞上控制窗口无关（6580/6582 为 +0.01s 撞上，6579/6581 为 +6.17/+6.46s 未撞上）。

因此可以回答上一轮留下的问题：**方向不是提高移动优先级或强行抢占，而是预站位与血量余量。**

### 2026-09-09 第二轮实施：近战 boundary 旁路（attempt 1788426595–1788426599）

#### 前锥模型被核心源码推翻并纠正

`WorldObjectSpellConeTargetCheck::operator()`（`src/server/game/Spells/Spell.cpp:9227`）的判定是：

```cpp
if (!_caster->IsWithinBoundaryRadius(target->ToUnit()) && !_caster->isInFront(target, _coneAngle))
    return false;
```

两个条件取**或**。`Unit::IsWithinBoundaryRadius`（`Unit.cpp:820`）用 `max(目标 bounding 半径, MIN_MELEE_REACH)`，对玩家即 **2.0 码**，并且**完全绕过角度判断**。因此：

- **站在 Ingvar 身上的近战无论在哪一侧都会被 effect 0 选中。**「绕背」从来不是近战的答案，「离开 2.0 码」才是。
- 这同时解释了此前一直无法解释的现象：六场里全部 30 条坦克 effect-0 记录都是 `front_60=false`。坦克贴身（`tank_range:boss_dist=0.000–0.500`）落在旁路内，角度检查根本没被执行。
- `Unit::GetMeleeRange` 对玩家打 Ingvar 为 `max(1.5+1.875+4/3, 5.0) = 5.0` 码，所以近战安全带是中心距 **(2.0, 5.0)**。

观察器的 `dst_dist` 口径也已核实：`WorldObject::GetDistance2d(x,y)` 只减去成员自身 `GetObjectSize()`（≈0.389），不减 Boss 的 combat reach。据此复核两次盗贼 effect-0：run256 97.145–97.402 秒 `dst_dist=0.00`（实际中心距 ≤0.4 码）、`front_60=false`，正是旁路命中；run259 88.16 秒前后盗贼从 5.50 一路走到 0.00，且当时坦克已在 69.94 秒死亡、盗贼在代坦。

#### 改动

- 近战后弧落点 **7.0 → 3.5 码**。7.0 码在 5.0 码近战射程之外，必然被 `reach melee`（落点约 4.1 码）拉回；这段往返正是近战反复越过 2.0 码旁路的来源。
- 贴身清理阈值 **1.5 → 3.0 码**。1.5 低于旁路半径，停在 1.7–1.99 码的近战既不触发清理、又照样被选中。
- 常量改为从 `kIngvarConeBypassRadius = 2.0f` 推导，注释直接写明核心源码出处。
- 另外：斧已进入 7 码伤害带时不再起手**新的**非瞬发法术。依据是 `PlayerbotAI::UpdateAI`（`PlayerbotAI.cpp:283`）在自身施法处于 `SPELL_STATE_PREPARING` 时会在跑引擎之前直接 `return`，那几个 tick 里触发器和动作一个都不会被求值——run250 的法师因此在斧上原地站了 4 秒（4 跳、13,675）。它只避免锁进新的读条，**不是完整修复，且本轮样本测不出效果**（见下）。

### 2026-09-09 第三轮：坦克其实有 3 秒可以躲（attempt 1788426600–1788426607）

上一轮把"坦克必须近满血"当成了下一步，前提是"坦克只能硬吃"。这个前提是错的。

#### 时序：存在完整的 3 秒可行动窗口

run249 首次 `59709` 的 root 窗口采样从 **67.983** 秒开始，而 `cast` 事件记在 **70.988** 秒，两者相差 3.005 秒 = 正好 3,000ms 读条时间。因此此前记录的 `cast` 事件时刻是**结算**，不是起手。同一批采样中坦克 `can_move` 在 67.983→70.750 全程为 **true**，只在 71.000（结算）变为 false——`59709` 的 effect 1 是 2 秒全队昏迷，属于结算的一部分。

配合脚本：`EVENT_SPELL_SMASH` 在施法时 `SetControlled(true, UNIT_STATE_ROOT)` 且 `DisableRotate(true)`，`EVENT_UNROOT` 在 3,750ms 后解除。所以整个读条期间 Boss 被定身、朝向冻结、全队未受控。**这是一个标准的可预读前向技能，不是必吃伤害。**

#### 为什么必须躲：P2 的 Dark Smash 是暗影伤害

| 阶段 | 法术 | 学派 | 基础伤害 | 坦克实际承受 |

| P1 | `59706` Smash | **物理** | 36,999–43,000 | 7,137–13,515（护甲约减 70%） |
| P2 | `59709` Dark Smash | **暗影** | 26,249–33,750 | 0 或 22,891 / 24,018 / 25,787 |

坦克血上限 28,884。P1 可以抗，P2 护甲无效、几乎全额进血条，且每 9–11 秒一次。那些 0 伤害不是抗住了，而是**运气**：run260 在 99.90 秒（结算同刻）触发了 `66233` Ardent Defender（60 秒一次的免疫致死打击），run263 被打死那次没有。

另外 `42751`（斧的每秒伤害）与 `59734` Dreadful Roar 同样是暗影，所以整个 P2 伤害构成都绕过护甲——这比全队昏迷更能解释 P2 为什么远比 P1 危险。

#### 为什么之前没躲

`IngvarDodgeSmashAction` 一直存在，但被两处挡住：

1. `isUseful()` 是 `return !behind;`。日志统计 **32 次 `behind=true useful=false`**（被判"在背后=安全"而跳过）、11 次 `useful=true`。而核心的选中条件是 `IsWithinBoundaryRadius(target) || isInFront(...)`，2.0 码旁路**不看角度**，贴身站在背后照样被选中。判据用错了。
2. 那 11 次执行时 `distanceExtra = 2.0f`，即穿过 Boss 后停在中心距**正好 2.0 码** = 旁路阈值本身，零余量。

#### 改动

`IngvarDodgeSmashAction` 改为继承 `IngvarGetBehindAction` 并复用 `MoveBehind(boss, MOVEMENT_FORCED, "smash_dodge")`：落点是冻结朝向的后弧、距 Boss 中心 3.5 码——同时不满足两个选中条件，且仍在 5.0 码近战射程内。`isUseful()` 改为直接问两个真实条件（`dist < 3.0` 或 `dist <= 10 且 HasInArc`），不再问角度。

#### 根因：`PrerequisiteX/Y/Z` 落在导航网格之外，成员到达即坠落

零位移导航探针（run294，终点 = 骑手平台传送点 `252.0,-350.0,185.8`）：

tiles=true/true

find_path=0x00000000                ← findPath 根本没有执行

tile 已加载，但该坐标在网格上**没有任何投影**（常规与扩大 Z 搜索都没找到最近多边形）。这与历史记录里 `(252.247,-350.532,185.813)` 的 `type=17` 一致，并把它从「路径不通」收窄为「该平台没有网格覆盖」。

#### 为什么改不成「从下层拉怪」

`Scenario.cpp:480` 的默认行为是 `_prerequisitePoint = _preparationPoint`，所以停用 `PrerequisiteX/Y/Z` 就能把集结点落回已实测可走的 `(245.60,-339.73,180.50)`。run295 试了这条路：**180 秒超时、0 死亡**——队伍活着但打不到骑手。原因是骑手在 5 码之上（`z≈184.95–188.79` 对 `180.50`），从下层对它们没有视线（`pull_rejected ... distance=10.x los=false`），而新增的接近步骤正确地拒绝了「走一条不存在的路线」，由既有的 180 秒上限兜住。

这与历史结论一致：「把准备点直接降到下层又会失去对上层骑手的视线」。此前 50 码邻域查询在该区域只找到 `(245.60,-339.73,180.50)` 这一个可走点，因此**当前 mmap 数据下不存在既在网格上、又对骑手有视线的坐标**，纯配置改动无解。

#### 结论与下一步

- 三骑手前置的不稳定**不是** bot 策略问题，也不是编排问题，而是 **map 574 上层骑手平台缺少 mmap 覆盖**。它与「完整副本自主行进」是同一个资产阻塞点。
- 隔离形态 `heroic-uk-ingvar-disc`（平台准备传送，无骑手）仍为 **9/9 击杀**，不受此影响。
- 官方场景另有一项独立差距：它没有 `-disc` 里已验证的角色分离准备点，且 `ValidateRoleSeparatedPreparation` 只是 `boss_start` 前的**位置门禁**、不会重新传送（`AttemptRunner.cpp:1222`），而角色分离传送只发生在登录阶段（`:233`）。所以要让官方场景也用上角色分离，需要在前置清理完成后补一次传送，属于独立改动。run291 的 boss 战段为 137 秒，明显长于隔离形态的 93.9–117 秒，与此一致。
- 下一步按序：(1) 分析 map 574 上层平台的 Recast 输入与栅格化，补出该平台的 mmap 覆盖；(2) 覆盖到位后再回归三骑手完整链路；(3) 前置完成后补角色分离传送。不得用猜测坐标或跨层传送绕过。

#### 框架修复：开怪门槛的假阴性（`CombatTrigger::BeginAssistForAll`）

测量一度被框架自身挡住：run 312/314/315 共 9 次 attempt 里有 **8 次**报
`pull failed (not all followers entered combat)`，装备夹具却全部 `valid=true`。

根因是 `alreadyAssisting` 判据过严。坦克建立仇恨后进入 assist 步时，跟随者往往已经把
boss 设为 `current target` 与 `victim`，但还没打出第一击，此时 `IsInCombat()` 与
`BOT_STATE_COMBAT` 都还是 false；`AttackAction` 对「已在攻击同一目标」按设计返回 false，
于是一次正常开怪被判成框架中止。命中与否取决于 tick 时序，所以表现为随机失败。

判据改为只看目标选择（`current target == boss && victim == boss`），不看 bot 自身战斗
旗标——boss 是否进入战斗已在上一步 `AwaitTankAggro` 确认过，跟随者是否真的输出由采样
证据体现，不由这道门槛断言。修复后 run 316 的 7 次 `already assisting` 全部来自实际
参战的 bot（伤害事件可核验），`could not begin assist` 归零，6 次 attempt 中 5 次开战。

### 2026-09-10 普通档 P2 走位优化：20% → 67%（run 317/318/321）

#### 共同根因：2.0 码 boundary 旁路

`WorldObjectSpellConeTargetCheck` 判定为
`IsWithinBoundaryRadius(target) || isInFront(target, coneAngle)`，而
`Unit::IsWithinBoundaryRadius` 走 `Position::IsInDist`——**纯 3D 中心距，不加体积**，
阈值 `max(目标 bounding, MIN_MELEE_REACH=2.0)`，对玩家恒为 2.0。所以中心距 < 2.0 码
时角度判定被完全绕过。上一轮已让坦克躲开这一带，但还有两条路径把别人送进去。

#### 缺陷 1：Killing Spree 与暗影猛击读条重叠（近战 DPS）

run316 三次团灭是同一条链，且完全确定性：

| 场次 | 盗贼稳定站位 | 跳变后 | Killing Spree | 猛击读条起点 | 结算伤害 |
|---|---:|---:|---:|---:|---:|
| 1 | 3.50 码 | 2.00 | 100,283（+1.26s） | 99,023 | 39,232 |
| 2 | 3.50 码 | 1.99 | 68,805（+0.42s） | 68,383 | 25,102 |
| 3 | 3.50 码 | 2.00 | 96,860（+1.22s） | 95,636 | 28,595 |

盗贼血上限 14,644 —— 必死。诊断里 `front_60` 恒为 false，正是旁路特征。这不是走位
逻辑没写好：Killing Spree (51690) 是 5 次瞬移连击，期间不可操控约 3 秒，正好覆盖
暗影猛击的 3 秒读条，位移把已经正确的站位推翻了。seq5 没有 Killing Spree，盗贼

### 2026-09-10 P2 团灭根因：Woe Strike（59735）把治疗打死

**结论先行**：普通档 P2 的团灭不是输出不够、不是治疗空转、不是法力、也不是仇恨，而是
**因格瓦尔的 Woe Strike 反射伤害把治疗打死**。本节同时保留本轮被证伪的两条假设，
避免下次重走。

#### 机制

Ingvar 英雄 P2 每 15–20 秒对坦克施放 **Woe Strike（59735）**，每场 4–7 次。Spell.dbc 描述：

> Deals X% of normal melee damage to an enemy and inflicts the target with Woe Strike.
> **Any healing the target receives while afflicted with Woe Strike deals Shadow damage to the healer.**

即：**坦克身上挂着它的时候，治疗每治疗坦克一次，就有一份暗影伤害直接打回治疗身上**
（触发法术 59736）。事件链逐条对得上——坦克 771 向治疗 772「施放」59736，同一毫秒
boss（60）对 772 结算伤害。

这解释了此前所有对不上的现象：治疗站在 **24.68 码**外（远超近战 5 码与暗影斧 5 码）
却在持续挨 boss 的伤害；**八场团灭治疗全部阵亡，其中五场是全队第一个死的**；
而它自己全程在正常治疗。观测器把这类伤害记为 `spell_id=0`，所以只看伤害表会误判成普攻。

#### 反射伤害是干净的成败判据

| 结果 | Woe 反射伤害合计 |
|---|---|
| 击杀（15 场） | 1,432 – 19,175 |
| 团灭（9 场） | **21,311 – 60,098** |

阈值约在 20,000。唯一越界样本是 run324/seq3（36,378，判为击杀但死了 3 人）。

#### 解法存在，覆盖率不足

Woe Strike 的 `Dispel = 2` = **诅咒**（用痛苦诅咒 980=2、腐蚀术 172=1、致命毒药 2818=4
校准过枚举；**注意 2 是诅咒不是魔法**，牧师的驱散魔法对它无效）。能解的是**法师的
「解除诅咒」（475）**，法师确实会用——全部普通档 run 合计放了 74 次。问题在覆盖率：

| | 每场 Woe 上身 | 法师解掉 |
|---|---:|---:|
| 各场次 | 4 – 7 次 | **0 – 4 次** |

大部分上身从未被解除。效果差别很直接：

- 上身后 3 秒内被解 → 该窗口 proc **0–7 次**
- 一直没解 → 该窗口 proc **3–24 次**

`PlayerbotAI::HasAuraToDispel` / `canDispel` 的判据本身没问题（`Dispel == dispelType`，
白名单里没有 Woe Strike，`DispelAuraDuration = 700` 也不构成阻挡）。**法师为什么漏掉
大部分上身尚未定位**——已知其中一个因素是法师本身会先死（run326/seq1 法师 79.3 秒阵亡），
但不足以解释全部。这是下一步要量的唯一一环。

#### 已证伪（保留，勿重走）

**假设一：`HealerAutoSaveManaMultiplier` 掐掉了快速治疗。** 该乘子非坦克分支确实少了
坦克分支才有的 `health >= lowHealth` 门槛，而快速治疗的 `HealingManaEfficiency::LOW`
是最低档、`manaEfficiency <= LOW` 恒真，看上去等于「法力低于 `SaveManaThreshold=60` 后
对非坦克的快速治疗被无条件掐掉」。日志里也确实抓到过
`Multiplier save mana made action flash heal on party useless`。**但补上门槛重编后
（run325）机制指标零变化**：快速治疗仍是每场 0–1 次、Shoot 仍是 15–21 次。对照组 run324
（只加只读采样、不改行为）3/5，run325 1/5，n=5 无法区分。**改动已回退**，
mod-playerbots 回到 `codex/heroic-uk-ingvar` 67ac953c。引擎日志显示快速治疗的真实拒绝
原因是 `SPELL_FAILED_NOT_READY`（GCD，49 次）、`UNIT_STATE_LOST_CONTROL`（26 次）与
自身苦修引导（15 次），`save mana` 只占 5 次。

**假设二：治疗在冷却间隙空转。** 第一版统计把**治疗阵亡之后的时间也算成了空档**，
于是团灭场显得空档 34–36 秒。按「存活期」重算后结论反转：

| | 存活期 P2 | GCD 利用率 | 空档合计 | 最长空档 |
|---|---:|---:|---:|---:|
| 击杀（12 场） | 50.5s | 60.3% | 25.1s | ≤12.1s |
| 团灭（8 场） | 30.0s | **62.7%** | 12.1s | ≤9.4s |

**团灭场利用率反而更高**，最长真实空档 9.4 秒与 Dreadful Roar 的 8 秒恐惧同量级。
所以「空转」不成立；真正的差别是**治疗活多久**（团灭 30.0s vs 击杀 50.5s）。
上一节写的「靶子是治疗在冷却间隙空转」据此作废。

**假设三：治疗拉到了仇恨。** 也不成立。boss 仇恨采样 133 个样本里，**132 个的当前目标
都是坦克**；唯一一次目标漂移发生在坦克为躲猛击退到 5.34 码（超出 5.0 码近战范围）的瞬间。
坦克仇恨 197k–202k，第二名仅 68k–73k。

#### 本轮新增的只读采样（mod-raidtest，行为中立）

`AttemptObserver` 增加两组，均只回读现成状态、不触发 `isUseful/CheckCast`：

- `heal_strategies` / `heal_actions`：治疗的 `Engine::lastAction`（需
  `AiPlayerbot.LogInGroupOnly = 0`，测完须改回 1）。
- `boss_threat`：boss 的 `GetLastVictim()`、仇恨表前二、坦克/治疗各自的仇恨值与到 boss 距离。

对照组 run324 为 3/5，与 65% 基线一致，证明采样本身不改变结果。
