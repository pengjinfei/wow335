# 上游同步与分支策略

## 1. 仓库与分支模型

本项目依赖两个高频更新的上游仓库：

| 仓库 | 上游基线分支 | 我们的开发分支 | 更新频率（观测） |
|---|---|---|---|
| `mod-playerbots/azerothcore-wotlk` | `Playerbot` | `dev` | 每周多次 |
| `mod-playerbots/mod-playerbots` | `master`（激进特性在 `test-staging`） | `dev` | **非常频繁**（SQL 更新几乎每天都有） |

```
上游（GitHub）                     本地
mod-playerbots/azerothcore-wotlk  azerothcore-wotlk/
    Playerbot ────────────────►  Playerbot （只读，永不提交）
                                      │
                                      └─► dev （我们所有改动在这）★

mod-playerbots/mod-playerbots      modules/mod-playerbots/
    master ───────────────────►  master （只读，永不提交）
                                      │
                                      └─► dev ★
```

**三条铁律**：

1. 上游分支（`Playerbot` / `master`）在本地**永远不直接提交**，只随
   `git pull --ff-only` 前进；
2. 我们的一切改动落在 `dev` 分支（机器人策略、补丁、本地配置脚本）；
3. 本管理库（`wow335/`）只存文档与脚本，不含上游源码（已 `.gitignore`）。

## 2. 日常同步流程

用封装脚本（见 §4）：

```bash
./scripts/sync-upstream.sh          # 只报告：落后多少、有无冲突风险
./scripts/sync-upstream.sh --apply  # 实际执行同步（fetch + dev 分支 rebase/merge）
```

手动版（理解原理用）：

```bash
cd azerothcore-wotlk
git checkout Playerbot && git pull --ff-only origin Playerbot
git checkout dev && git merge Playerbot          # 或 rebase，见下

cd modules/mod-playerbots
git checkout master && git pull --ff-only origin master
git checkout dev && git merge master
```

**merge 还是 rebase？** 推荐 **merge**：历史真实、不重写提交；上游冲突多时
merge 一次解决一批。若某次同步冲突极少且想保持线性历史，可用
`git rebase <上游分支>`（仅当 `dev` 未推送到任何远端时才随意 rebase）。

## 3. 冲突处理原则

- 冲突几乎只会出现在**双方都改了同一文件**时。我们对核心的改动应尽量走
  官方扩展点（模块、`data/sql/custom/`、conf 覆盖），少改核心源文件——
  这是冲突最少、也最方便将来向上游提 PR 的做法。
- 模块仓库（mod-playerbots）是我们主要改动的地方（策略代码），与上游冲突
  时：逐文件人工合并，**以保留上游机制 + 叠加我们的策略**为原则；解完后
  跑一次编译再提交。
- 数据库增量由 DatabaseUpdater 自动应用，无需手工迁移；但**自己的自定义
  SQL 一律放 `data/sql/custom/`**（核心）或模块的 `custom` 约定位置，避免
  与上游文件名冲突。

## 4. sync-upstream.sh 行为说明

脚本 `scripts/sync-upstream.sh`：

- 默认（无参数）：对两个仓库 `git fetch`，打印"本地基线落后上游 N 个提交"
  与 `dev` 分支状态，**不做任何修改**；
- `--apply`：在基线分支执行 `pull --ff-only`，然后把基线 `merge` 进 `dev`；
  遇到冲突会停下并提示手工处理（不会乱来）；
- `--submodule-status`：显示两边当前 HEAD 的提交哈希，便于记录"哪个上游
  版本跑通了什么"。

建议节奏：**模块仓库每周至少同步一次**（它迭代快，落后太多冲突面会变大）；
核心仓库在每次要动核心代码前同步一次。

## 5. 何时升级到 GitHub 远端（可选）

当需要备份或跨机器工作时：

```bash
brew install gh && gh auth login
gh repo fork mod-playerbots/mod-playerbots --clone=false      # fork 到自己账号
# 模块仓库挂上自己的远端
cd azerothcore-wotlk/modules/mod-playerbots
git remote add mine https://github.com/<你的账号>/mod-playerbots.git
git push -u mine dev
# 核心 fork 同理（gh repo fork mod-playerbots/azerothcore-wotlk）
```

之后同步脚本不受影响；`dev` 分支多了远端备份而已。
跨机器的开发环境复制则直接用本管理库（`wow335/`）的文档 + 脚本重走一遍
`docs/02-环境搭建手册`。

## 6. 上游破坏性变更的应对

- 模块仓库的 `data/sql/playerbots/updates/` 每天都有新文件——这些启动时
  自动应用，一般无痛；若某次启动 SQL 报错，先看该次同步带来的新 SQL 文件。
- 核心仓库 `Playerbot` 分支偶发 API 变化（bot 接口、Hook 签名）。同步后
  编译失败时：`git log dev..Playerbot --stat` 看变了什么；模块侧报错通常
  意味着模块仓库也需要同步到配套版本（两个仓库配套演进，**建议总是一起同步**）。
